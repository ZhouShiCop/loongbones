## 已定案（负责人 2026-10-19）

1. **原则上采用 C++17 + Qt Widgets + OpenGL + CMake。**
2. **先进行可撤销的对比实验**，确认三件事可行后再固化本 ADR：
   - Qt Widgets 的多面板布局可行（规范 §5 Phase 5 的 Blender 式 workspace）
   - OpenGL 视口集成可行
   - 构建环境可行
3. **Domain 必须独立于 Qt**；**渲染后端通过接口隔离**（规范 §3.1、§8.3）。
4. **不得仅因技术选型实验而扩大任务范围。**

## 为什么"原则已定"而非"已固化"

负责人要求先做可撤销实验再固化。因此本 ADR 的对比结论（下列"候选评估"）作为
实验的**设计输入**，不是最终结论；实验完成后由负责人签定并把状态改为"已固化"。

## 候选评估（实验输入，非结论）

| 方案 | 优势 | 风险 / 成本 |
|---|---|---|
| **A. C++ + Qt Widgets + OpenGL** ← 原则选定 | 性能最好；Blender 式多面板/停靠最贴合 Widgets；生态成熟；无运行时依赖 | 开发速度慢；需自有 OpenGL 抽象层；大网格/长 timeline 需自行虚拟化 |
| B. C++ + Qt Quick (QML) | 声明式动画/过渡，做时间轴 UI 快 | Scene Graph 与"每帧重算蒙皮"集成复杂；大数据量列表需 delegate 优化；调试链长 |
| C. Python + PySide6 | 原型最快；数值验证脚本可复用 | 运行性能（Phase 6 有大样本压力测试）；分发体积/依赖；与 Domain 需 C 加速时割裂 |

### ⚠️ 待确认风险：工具链与 Qt 的 ABI 一致性

若 Qt 最终以 **MSVC** 方式安装，则 MinGW 编译的核心库与 MSVC 的 Qt 应用之间存在
**ABI/C++ 运行时不一致**（两者 C++ 标准库与异常机制不同）。
处置选项（**尚未决定，需在 Qt 装完后确认其编译器**）：

1. 若 Qt 用 MinGW → 当前工具链直接可用，无问题。
2. 若 Qt 用 MSVC → 核心库需改用 MSVC 重建；或
3. 核心库对外接口改为 **pImpl / C ABI**，切断跨编译器的 STL 类型边界（增加实现复杂度，
   规范 §8.3 要求论证必要性，故不预先实施）。

**本项列入"待验证/待确认"，不写成已解决。**
