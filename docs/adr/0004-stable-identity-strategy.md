# ADR-0004 稳定 ID 策略与索引迁移

- 状态：**已定案（2026-10-20）：全部持久化对象使用随机 ULID**
- 日期：2026-10-19
- 阻塞：对象引用模型、权重绑定、导入映射
- 关联：规范 §3.2（编辑事务与稳定标识）、§4（向后兼容）、§10.1（持久化对象使用不可变 ID）

---

## 1. 背景与真实约束

规范 §3.2 已定：对象间引用以不可变 `id` 为主，名称仅用于展示且**可重命名而不使链接失效**；
数组/列表顺序作为显式语义保存，不依赖哈希映射迭代次序。

Spine 3.2.01 侧大量使用**数组下标/名称寻址**（bone `parentIndex`、slot `bone`、
加权 mesh `vertices` 内的 `boneIdx`、IK 约束 `bones[]`、`linked mesh` 的 `parent`/`skin`），
导入时必须整体迁移到 ID 寻址。

**当前阶段的范围边界（Phase0Back §4）**：Task 1 只做图片/图层/简单组合，
Spine 动画数据、约束与高级附件**不进入本阶段 Schema**。
因此本 ADR 的"导入"部分在 Phase 1 内**不需要实现**，但 ID 契约必须现在定死，
因为 Task 1 的 `Project`/`Node`/`ImageAsset` 都要 ID，而**改 ID 策略＝破坏性变更**。

---

## 2. 三个方案

| | A. 全部随机 UUID | B. 全部确定性派生 | C. 混合 |
|---|---|---|---|
| **生成方式** | 每次新建都随机 | `ID = f(源标识, 稳定键)` | 新建→随机；导入→有源 ID/稳定键则派生，否则随机 |

---

## 3. 逐维度对比

### 3.1 重复导入

**先分清两件事（负责人指出，属独立业务策略，不由 ID 算法决定）**：
- 策略 i「去重复用」：再次导入同一素材 → 复用已有对象
- 策略 ii「创建副本」：再次导入 → 用户想放两份

| | A | B | C |
|---|---|---|---|
| 策略 i（复用） | 可行：按业务键查已有对象，不看 ID | **天然有利**：同源 ⇒ 同 ID，识别即复用 | 有利：导入走派生路径 |
| 策略 ii（副本） | 可行：新随机 ID | **危险**：同源 ⇒ 同 ID ⇒ **同工程内 ID 冲突**；必须引入"实例序号/副本路径"消歧，派生逻辑变复杂 | 可行：副本这一层用随机 ID |

> **关键结论**：确定性派生只对「去重复用」有利，对「创建副本」是负担。
> 若产品确定要支持"同一素材放两份"，纯 B 就得为副本单独设计一套 key，复杂度反超 C。

### 3.2 复制对象（工程内）

| | A | B | C |
|---|---|---|---|
| | 新随机 ID，天然安全 | **必须换新 ID**，但"确定性"承诺被打破——需要显式的 `copySuffix` | 新建走随机，天然安全 |
| diff 可读性 | 复制件在 diff 里表现为"全新对象"，语义清晰 | 需额外标记"派生自 X 的副本" | 同 A |

### 3.3 跨版本迁移

| | A | B | C |
|---|---|---|---|
| | ID 不变，迁移只改内容 → **最简单** | ID 稳定 → 简单 | 导入对象稳定，新建对象不变 → 简单 |

三者都可接受；A 在这里略优（因为 ID 不携带任何可被误当作语义的信息）。

### 3.4 回归 fixture

| | A | B | C |
|---|---|---|---|
| 新建对象 ID | 每次不同 → golden 文件需"忽略 ID 归一化"或把 ID 钉死在 fixture | 稳定 | 导入部分稳定、新建部分随机 |
| 实现代价 | 归一化工具或固定 ID | **无需归一化** | 归一化仍需处理新建对象 |

> **这是 B 唯一的明显优势**，且优势不小：规范 §7 要求验收依赖"关键数值/计数"，
> §8.4 要求"文件格式用历史 fixtures、迁移往返"。ID 稳定能让 fixture 逐字节可比。

### 3.5 diff / 合并

| | A | B | C |
|---|---|---|---|
| 同源工程对比 | 无法用 ID 对齐，要靠内容/路径匹配 | **可直接按 ID 对齐** | 导入部分可对齐 |
| 当前阶段实际需要 | 低（单用户单机工具，无合并需求） | 中 | 低 |

规范 §5 Phase 5 提到"动画混合/多轨道仅在明确需求和模型设计通过后加入"，
说明**当前没有合并/协同需求** → 这一维的权重应当压低。

### 3.6 ID 冲突

| | A | B | C |
|---|---|---|---|
| | 不冲突 | **可能冲突**：不同语义碰撞，或同源重复（见 3.1） | 随机兜底，永不冲突 |
| 冲突处理 | 无需 | 必须有消歧策略 + 诊断 | 退化到随机 |

### 3.7 实现复杂度

| | A | B | C |
|---|---|---|---|
| 核心模型 | 最低：生成 + 唯一性检查 | 中：+ 稳定键选取 + 冲突消歧 | 中高：两条路径 + 判定 |
| 导入器 | 需 ID 映射表 | 天然自带映射 | 需映射表 |
| 诊断 | 少 | 多（冲突/退化） | 中 |

## 4. 对比小结

| 维度 | A 随机 | B 确定性 | C 混合 |
|---|---|---|---|
| 重复导入（副本策略） | ✅ | ❌ 需额外设计 | ✅ |
| 重复导入（复用策略） | 可行 | ✅ | ✅ |
| 工程内复制 | ✅ | ⚠️ 破坏确定性承诺 | ✅ |
| 跨版本迁移 | ✅ | ✅ | ✅ |
| 回归 fixture 稳定 | ❌ 需归一化 | ✅ 免归一化 | ⚠️ 部分需归一化 |
| diff/合并 | ❌ | ✅ | ⚠️ |
| ID 冲突 | ✅ | ⚠️ | ✅ |
| 实现复杂度 | 最低 | 中 | 中高 |
| 当前阶段是否够用 | ✅ | ✅ | ✅ |

**没有任何方案在所有维度占优**：
- A 最简、最安全，但**回归 fixture 与 diff 要额外归一化**（规范 §7/§8.4 都依赖这两项）
- B fixture/diff 最优，但**与"创建副本"这条业务路径天然冲突**
- C 覆盖最全，但复杂度最高，而其中一部分能力（diff/合并）**当前阶段并不需要**

---

## 5. 最终决策

**最终采用 A（随机 ID）**。导入 ID 不采用源内容 hash 派生；该决定遵循 D25。

理由：

1. **「创建副本」是资产组合器的常见需求**（同一图放两份是基本操作），
   纯 B 会让这条最常见的路径背上"确定性"的包袱。因此排除纯 B。
2. **规范 §7/§8.4 把回归 fixture 与可复现验收列为硬要求**，纯 A 需要额外维护归一化工具，
   而工具本身也要被登记与维护。所以"全随机"也不是零成本。
3. **但当前阶段不需要为不需要的能力写代码**（规范 §8.3）。
   Task 1 无导入、无 diff/合并 ⇒ 此刻只有"随机 ID"这一条路径会被执行。

落地规则：

| 阶段 | 落地内容 |
|---|---|
| 所有新建/导入对象 | 使用宿主统一的随机 ULID 工厂；工程内复制与重复导入都会获得新 ID |
| 导入引用映射 | 稳定键仅用于单次导入内将父子、槽、附件等引用解析到分配后的 ID |
| 来源与重复提示 | 持久化 sourceRef 可记录 hash 与逻辑来源；hash 不参与 ID 生成。重复导入默认创建副本 |
| 未来显式更新/重导 | 若实现，按已持久化的 source-key→ID 映射沿用已有 ID；禁止对当前内容重新 hash 派生 ID |

### 5.1 ID 形式建议：ULID

规范 §10.1 允许「UUID/ULID 或等价方案」。建议 **ULID**（26 字符 Crockford Base32）：

- 时间前缀 ⇒ ID 天然按创建顺序排序，对 Outliner / Asset Browser 的稳定排序直接有用
- 可自行实现（约 20 行：48 位毫秒时间 + 80 位随机），**无需第三方依赖**
  （规范 §8.3 要求新增依赖前论证，故优先零依赖实现）
- 大小写不敏感，可读；非法字符集排除，天然抗输入污染

ID 契约（写入 schema 注释）：
- **不可变**：创建后任何操作不得改写
- **不含语义**：不得由名称、数组位置、文件路径推导（规范 §10.1）
- **重命名不影响 ID**
- **区分大小写敏感性**：ULID 规范形式为大写；读取时容忍小写，写出统一大写

### 5.2 已关闭的决策问题

1. ID 策略：随机（A），不做 hash 派生。
2. ID 形式：ULID。
3. 重复导入：默认创建副本；任何链接已有或更新已有的行为必须由用户显式选择。

## 6. 验证入口

- Task 1：`tools/core-tests/` 需覆盖"随机 ID 不重复"、"ID 不因重命名改变"、"ID 不由名称/位置推导"
- Phase 2（导入）：增加"同一素材导入两次 → 两次得到的 ID **不相同**，且各自合法
  （默认创建副本，D25）"、"复制操作产生新 ID"两个用例
- 另需一个 fixture 归一化工具（把随机 ID 替换为稳定占位），
  以便 golden 文件逐字节可比——**是否现在就做，取决于是否现在就用随机 ID**；
  若采纳本推荐（当前随机），则该工具在 Phase 1 建工程格式时再建。
- 若将来实现"显式更新/重导并沿用 ID"：必须基于**已持久化的 source-key → ID 映射**，
  且由用户显式触发；不得对当前内容重新 hash 派生 ID（D25）。
